MindCLI 计划 JSON 对比：/plan vs /team

两个模式都输出同一套「任务 DAG」计划 JSON，共用解析与校验层；真正的区别在 prompt（v2/v3）、JSON 字段多寡，以及拿到计划后由谁、怎么执行。

所有结论均来自源码，路径引用已标注到具体文件与行号。

5 · 共用解析层（最容易被忽略的真相）▾

两个模式共用 4 个类，解析出的结果类型也完全一致：

PlanSchemarecord PlanSchema(int schemaVersion, String summary, List<PlanTaskSpec> tasks)（PlanSchema.java:5） PlanTaskSpec12 个字段的 record，已包含 v3 全部新字段（PlanTaskSpec.java:5-18） PlanSchemaParserparse(rawJson)，会 strip 代码围栏、读 tasks/steps 两种键（PlanSchemaParser.java:18） PlanSchemaValidatorvalidate(schema)，校验 id 唯一、type、依赖存在、无自依赖、无环（PlanSchemaValidator.java:12）

分叉点：从 PlanTaskSpec 到执行模型

模式转换方法产物
planPlanner.buildExecutionPlan()（Planner.java:88） ExecutionPlan（内部 Map<String,Task>，拓扑排序 executionOrder）
teamAgentOrchestrator.parsePlan()（AgentOrchestrator.java:763） List<ExecutionStep>（不可变 record，含 StepStatus）
❓ 面试点 「为什么解析层要共用而不是拆两套？」—— 计划本质都是「带依赖的任务 DAG」，schema 只是字段超集。 共用能统一兜底（类型推断、循环检测、PlanRepairer 修复），避免两套校验逻辑漂移； 版本通过 prompt 而非代码分叉演进。

6 · 状态流转图（Task / ExecutionStep 生命周期）▾

plan 模式用 Task.TaskStatus，multi-agent 用 StepStatus， 两者状态集一致（PENDING / RUNNING / COMPLETED / FAILED / SKIPPED）。虚线回路表示瞬态错误重试。

⚠️ 易错 依赖判定里 COMPLETED 和 SKIPPED 都算「满足依赖」， 但 FAILED 不算——下游会一直阻塞，直到重试、重规划或整条计划标记失败 （见 Task.isExecutable() Task.java:192 与 ExecutionPlan.getExecutableTasks() ExecutionPlan.java:101）。

7 · 执行与失败恢复机制对比 ▾

plan 模式：三级递进恢复（PlanExecuteAgent.java:394-444）

plan 模式的恢复：瞬态错误重试 → 显式 SKIP/BLOCK 降级 → 默认 REPLAN 局部重规划子树。

multi-agent 模式：委派 + 自审循环（AgentOrchestrator.java:1227）

阶段机制关键点
选人acquireForStep → AgentPool.acquire preferredAgent 优先，否则只读/写入二分
执行executeWorkerChild → SubAgent.executeWithContext 每个 step 独立 PrintStream 缓冲，批次结束后按 id 顺序 flush
自审executeSelfReviewChild → parseReviewApproval 执行者自己 review 结果，approved 决定是否放行
重试MAX_RETRIES_PER_STEP = 2（AgentOrchestrator.java:75） 不通过则带反馈重执行，超限标 FAILED
写隔离runMutatingBatchParallel（AgentOrchestrator.java:542） git worktree 隔离并行写，merge 冲突标 FAILED 不静默覆盖
❓ 面试点 「为什么 multi-agent 要引入 writeScope？」—— 多代理并行写文件可能互相覆盖； writeScope 让可并行步骤互不重叠（many readers, one writer），重叠时要么串行、要么 worktree 隔离后 merge。 plan 模式是单 agent，串行/受控，不需要这个。

8 · 面试追问方向 ▾

  1. 「为什么 v3 要引入 writeScope？」 —— 多代理并行写隔离，见上。
  2. 「为什么解析层共用而非拆两套？」 —— 计划本质是带依赖的任务 DAG，schema 是字段超集；共用统一兜底、避免逻辑漂移。
  3. 「schemaVersion 不校验，怎么保证 LLM 输出 v3？」 —— 靠 prompt 约定 + PlanRepairer 解析失败回炉修复；正确性由 validator 的结构校验兜底（id 唯一、无环、依赖存在），这是「软约束」设计。
